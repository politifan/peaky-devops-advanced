Копия и восстановление без перезаписи источника
Учебные условия: RPO ≤ 5 минут, RTO ≤ 10 минут; это цели упражнения, не измеренные свойства системы. RPO — граница потери последних записей, RTO — время от инцидента до принятой полезной операции. Время выполнения restore.py само по себе не равно RTO.
До эксперимента записать old_id и old-ticket.json из stage. Установить момент последней принятой записи UTC. Остановить CI, Locust и все посторонние писатели; api stage масштабировать до 0 и дождаться удаления Pods как в модуле 8. DB остаётся работающей.
./lab guard./lab backup --namespace stage --other-writers-stoppedkubectl --context kind-dva-course -n stage scale deployment/ticket-api --replicas=2kubectl --context kind-dva-course -n stage rollout status deployment/ticket-api --timeout=120s
Скрипт печатает новый каталог backups/. Записать его точное имя в backup_dir; не выбирать «последний» по догадке. Сохранены snapshot всех id/title/status + Alembic revision, custom dump, SHA256, image_ref и manifest. Snapshot и dump сделаны последовательно: согласованность требует остановки всех писателей, одной лишь pg_dump консистентности недостаточно для равенства двух снимков. Флаг подтверждает действие оператора, а не автоматически обнаруживает всех внешних клиентов.
После копии создать отдельную новую заявку в stage, сохранить её id/title и время. Эта запись намеренно отсутствует в копии. Источник остаётся целым; упражнение имитирует возврат к точке копии, не требует портить рабочую БД.
restore_ns=restore-$(date -u +%Y%m%d%H%M%S)./lab restore "$backup_dir" --destination "$restore_ns"kubectl --context kind-dva-course -n "$restore_ns" get pvc -o wide
Создаётся новый namespace и новый PVC. Если namespace уже существует, скрипт отказывает, не восстанавливает поверх. Он проверяет hash, создаёт владельца, восстанавливает без старых ACL под ticket_app, возвращает минимальные права ticket_runtime, сравнивает все записи и revision, поднимает API с image_ref из копии. Текущие учебные Secrets берутся из source namespace: для настоящей потери исходного кластера нужен отдельный защищённый план получения credentials, которого этот стенд не реализует.
В отдельном терминале:
kubectl --context kind-dva-course -n "$restore_ns" port-forward service/ticket-api 18240:8000 --address 127.0.0.1
В основном до HTTP цикла подтвердите отсутствие post-copy заявки. Её id сохраните из источника в переменной post_copy_id, ожидаемый title запишите отдельно:
curl --silent --output evidence/m09-post-copy-before.json --write-out '%{http_code}\n' "http://127.0.0.1:18240/tickets/$post_copy_id"curl --silent --output evidence/m09-source-post-copy.json --write-out '%{http_code}\n' "http://127.0.0.1:18230/tickets/$post_copy_id"
Restore ожидает404, источник200 и исходные поля. curl без --fail может дать exit0 при404: HTTP status и код клиента различайте. Затем:
./lab http --base http://127.0.0.1:18240 --read-id "$old_id" --expected .runtime/old-ticket.json --out evidence/m09-restored-http.json
Сравнение SQL выполнялось до этой проверки: HTTP создаёт новую синтетическую запись. Восстановленная sequence может вновь использовать post-copy числовой id. После новых записей id недостаточно: сравнивайте title/status и происхождение. Источник должен по-прежнему отдавать первоначальную post-backup заявку.
Записать UTC начала имитируемого инцидента, начала/конца restore, первого успешного HTTP. Посчитать полное RTO и фактическое окно потерянных событий относительно copied data, указать точно одну намеренно отсутствующую запись до новых записей. Размер и hash не доказывают восстановление: требуется SQL и HTTP. Копия вне рабочего PVC, но на том же физическом хосте — не защита от потери диска ноутбука. pg_restore.
Если restore остановился, сохранить точный этап/код, состояние нового namespace, причину и повтор в новом destination после исправления. Исходный namespace/PVC не трогать. В итоговом postmortem отделить наблюдавшееся от предположений.

Ограниченная Python-нагрузка
Использовать только собственный dev NodePort http://127.0.0.1:18220. Port-forward Service выбирает отдельный Pod и непригоден для вывода о балансировке двух Pods. API/БД должны быть исправны, чужие нагрузки остановлены. Начальный профиль: 10 пользователей, spawn 2/s, 60 секунд измерения, wait 0.1s, GET:POST веса 4:1. Это доли выбора задач, фактические counts отличаются из-за длительности запросов.
python3 -m venv .venv-load.venv-load/bin/pip install -r load/requirements.txt./lab http --base http://127.0.0.1:18220 --out evidence/m10-preflight.jsonhelm get values ticket-dev --kube-context kind-dva-course -n dev -o yaml > .runtime/m10-values.yamlhelm upgrade ticket-dev chart --kube-context kind-dva-course -n dev -f .runtime/m10-values.yaml --set resources.limits.cpu=100m --wait --atomic --timeout 180s.venv-load/bin/locust -f load/locustfile.py --host http://127.0.0.1:18220 --headless -u 10 -r 2 -t 15s --csv evidence/warmup.venv-load/bin/locust -f load/locustfile.py --host http://127.0.0.1:18220 --headless -u 10 -r 2 -t 60s --csv evidence/before-1 --csv-full-historypython3 load/analyze.py evidence/before-1_stats.csv > evidence/before-1-summary.json
Warmup не включать в measured CSV. Продолжительность с ramp-up одинакова во всех сериях, отдельного постоянного плато здесь не выделено. Записать commit/digest, replicas/requests/limits, DB Pod/PVC, число заявок до/после, состояние хоста, Locust версию. Данные POST растут: это отдельный фактор. Не заявлять идентичный dataset, если начальное число строк изменилось; для строгого сравнения поднимать отдельную копию одинакового snapshot в учебном namespace и повторять NodePort setup, либо объяснить ограничение текущей серии.
До и во время каждого прогона собрать выбранные Pod names; в отдельном терминале на каждом API Pod выполнить kubectl --context kind-dva-course -n dev exec <pod> -- python ops/resource_sample.py и сохранить вывод. cgroup v2 cpu.stat содержит throttling, memory.current и CPU quota; интервал измеряет потребление контейнера, не всю машину. kubectl top не обязателен: metrics-server в комплекте нет. Также наблюдать CPU генератора и хоста доступными системными средствами, DB задержки через HTTP/логи, restart/OOM events.
Повторить три baseline прогона с разными именами. Гипотеза: CPU limit100m повышает p95 через throttling. Исходные release values сохранены до baseline, поэтому image.ref/digest и releaseLabel сохраняются. Для after:
helm upgrade ticket-dev chart --kube-context kind-dva-course -n dev -f .runtime/m10-values.yaml --set resources.limits.cpu=500m --wait --atomic --timeout 180s
Requests/replicas/image не менять, провести такой же warmup и три after с другими CSV именами. Если throttling не наблюдается или RPS не вырос — гипотеза не подтверждена; это допустимый вывод. Вернуть исходные values и проверить HTTP:
helm upgrade ticket-dev chart --kube-context kind-dva-course -n dev -f .runtime/m10-values.yaml --wait --atomic --timeout 180s./lab http --base http://127.0.0.1:18220 --out evidence/m10-final-http.json
p95 считать отдельно для GET и POST по CSV, ошибки включают contract validation. Не усреднять GET/POST p95 для общей квантиля. Общая частота ошибок = сумма failures / сумма requests. Пропускная способность полезных операций требует успешных counts и фактического интервала, а не просто максимального users. Median трёх p95 — сводка прогонов, не p95 всех запросов. Указать разброс/минимум/максимум.
При росте ошибок >5%, OOM или нехватке диска остановить генератор, исправить стенд, сохранить неполный CSV отдельно, затем повторить с тем же профилем. На одном ноутбуке API, PostgreSQL и Locust конкурируют за CPU: не переносить цифры на промышленную инфраструктуру. Locust.
